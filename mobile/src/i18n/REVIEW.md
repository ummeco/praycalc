# i18n String Extraction — Human Translation Review Tracker

Generated by the P2 i18n string-extraction pass over `src/features/**` and
`src/app/**` (excluding `home-widget/HomeWidgetStub.tsx` and `src/widgets/**`,
owned by another workstream) plus `src/components/shared/UIStates.tsx` and
`src/components/states/index.tsx`.

## How to read this table

- **en** — the source string (always present, 100% coverage — 374 keys total).
- **ar / ur** — Arabic and Urdu got the deepest generic-UI whitelist coverage
  (24 new `common.*` keys + 6 `tabs.*` + 2 `menu.*.label` on top of the fully
  translated pre-existing `app/prayer/common/greeting/settings/errors`
  namespaces already in the repo).
- **other 18 locales** (fr, tr, id, ms, bn, sw, es, de, nl, pt, it, ru, hi, ps,
  fa, so, ha, yo) — 18 new keys each (`common.*` whitelist minus the ar/ur-only
  extras, plus `tabs.*` + 2 `menu.*.label`).
- **fallback to en** — every other key added in this pass (all `screens.*`
  namespace, most of `settings.*`, `menu.*.subtitle`) is present ONLY in
  `en.json`. i18next's `fallbackLng: 'en'` means these render in English in
  every locale until a human translator fills them in. This is intentional —
  see the Hard Content Gate below.
- **needs human review** — flagged where the English source itself contains
  fiqh/religious nuance and a future translator must consult a qualified
  reviewer before translating, not just do a literal translation.

## Hard Content Gate — What Was NEVER Machine-Translated

Per the release-gate rule (Islamic content correctness), the following stayed
English in ALL non-en catalogs and were NOT touched by this pass at all:

- Dua/dhikr Arabic text, transliteration, translation, and source citations
  (`DuaDhikrScreen.tsx`, `TasbeehScreen.tsx`, `RamadanScreen.tsx` dua data
  arrays — `MORNING_ADHKAR`, `EVENING_ADHKAR`, `POST_PRAYER_DUAS`,
  `DHIKR_PRESETS`, `RAMADAN_DUAS`). These are literal Hisn al-Muslim / Sahih
  Bukhari+Muslim citations — never extracted to catalogs, never
  machine-translated.
- Quran text and translations (`QuranScreen.tsx` — `AL_FATIHA_AYAHS`, surah
  metadata Arabic names) and the Quran 2:189 citation in `MoonScreen.tsx`.
- Fiqh explanations: qasr/jama notes in `TravelScreen.tsx`
  (`screens.travel.musafirAlertBody`, `screens.travel.fiqhNote`), the
  Ramadan/Laylat al-Qadr notes in `RamadanScreen.tsx` and `MoonScreen.tsx`
  (`screens.ramadan.laylatAlQadrBody`, `screens.moon.ramadanNote`,
  `screens.moon.dhulHijjahNote`), and the "rak'at" unit labels in
  `TravelScreen.tsx`.
- `common.bismillah` and `greeting.assalamu_alaykum` (pre-existing keys,
  already fully translated per-locale before this pass — untouched).

These religious-adjacent `screens.*` keys exist ONLY in `en.json` and are
flagged **needs human review** below — a qualified translator/reviewer must
translate them, not a machine pass, because getting fiqh nuance wrong is a
release-blocking error per PPI theology standards.

## Locale-Aware Date/Time Formatting (no catalog entries — code-level i18n)

The following were switched from hardcoded `'en-US'` / English arrays to
`toLocaleDateString(i18next.language, ...)` / `toLocaleTimeString(i18next.language, ...)`:

- `IslamicCalendarScreen.tsx` — weekday labels (`getWeekdayLabels`) + month name (`getMonthName`) + Gregorian date header
- `TimetableScreen.tsx` — month name (`getMonthName`) + per-day time formatting (`formatTime`)
- `PrayerTimesScreen.tsx` — Gregorian date header + per-prayer time formatting (`formatTime`)
- `RamadanScreen.tsx` — Suhoor/Iftar time formatting (`formatTime`)
- `MoonScreen.tsx` — next full/new moon date formatting
- `StatsScreen.tsx` — weekly bar-chart day labels (`getWeeklyData`)

The Hijri month names module (`src/lib/hijri`) was left untouched — proper-noun
transliterations (Muharram, Safar, etc.), not translatable UI strings, per task
instructions.

## Intentionally Left Hardcoded (not i18n keys, and why)

- Internal identifiers: `PrayerName` union values (`'Fajr'`, `'Dhuhr'`, etc.),
  store keys, route paths, analytics event names, `AuthTab` union values,
  `MoonPhase` union values, `DuaCategory` union values — all stay English by
  design (render-time translation happens via a `*_LABEL_KEYS` lookup map
  pattern already established in the codebase, e.g. `PRAYER_LABEL_KEYS`,
  `MOON_PHASE_LABEL_KEYS`, `ACCURACY_LABEL_KEYS`).
- Device-calendar event content in `AgendasScreen.tsx` (`title: `${name}
  Prayer`` and `notes: 'Salah time — PrayCalc'` passed to
  `Calendar.createEventAsync`) — this is data written into the OS calendar
  app, not in-app UI text; translating it was out of scope for this pass
  (flagged as a candidate for a future ticket, not blocking).
- Dua `occasion` field values in `RamadanScreen.tsx` (e.g. "At iftar time",
  "Before Tarawih") — part of the religious content data structure alongside
  the Arabic/transliteration/translation/source fields in the same array;
  treated as content, not chrome.
- `LOCALE_NAMES` table in `src/i18n/index.ts` (native language display names
  for the language picker) — proper nouns, not translatable UI strings;
  already complete and untouched.
